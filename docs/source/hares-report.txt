                                          ABSTRACT

The rapid adoption of AI tools like ChatGPT and Gemini in workplaces has created a serious risk
of unintentional data leakage, as employees unknowingly share sensitive information such as
passwords, API keys, and personal data with these platforms.
Hares AI is a browser extension that intercepts user input before submission, analyzes it locally
on the device, and alerts or blocks the action if sensitive data is detected without sending raw
sensitive data to external servers.
The goal of this project is to provide a lightweight, privacy-preserving solution that protects
organizations from AI-related data exposure.

1.​ Introduction

The rise of artificial intelligence tools has fundamentally changed how people work. Platforms
such as ChatGPT, Google Gemini, and Claude are now deeply embedded in daily workflows
across industries helping employees write reports, generate code, analyze data, and make
decisions faster than ever before.

However, this convenience comes with a hidden cost. Employees routinely paste sensitive
information into these platforms without considering the consequences. API keys, passwords,
personally identifiable information (PII), confidential contracts, and proprietary source code are
all being shared with external AI servers on a daily basis. In most cases, this happens
unintentionally the user simply does not realize the risk.

Organizations are increasingly aware of this threat, yet few practical solutions exist that operate
at the point of input where the risk actually begins. Existing security tools focus on network
monitoring or post-incident response, leaving a critical gap in real-time prevention.

Hares AI addresses this gap directly. It is a browser extension that sits silently between the user
and any AI platform, intercepting input before it is submitted, analyzing it locally on the user's
device, classifying the risk level, and immediately alerting or blocking the action when sensitive
data is detected. No raw sensitive data leaves the device during this process. In cases where
Regex-based detection is inconclusive, the system sends only the ambiguous text segment after
masking any previously identified sensitive content with placeholder tags to the Gemini API for
further classification, ensuring that no exposed sensitive data is transmitted externally.

The objective of this project is to build a lightweight, accurate, and privacy-preserving tool that
protects organizations from AI-related data leakage without disrupting the user's workflow. The
system is designed to be simple enough for any employee to use, yet powerful enough to meet
the security needs of modern organizations.

3.​ Risk/Constraints

3.1 Constraints

3.1.1 Local Detection Performance: A primary constraint is the limited computational power of
client-side browsers. Since Hares AI performs its primary detection locally using Regex patterns,
the detection engine must be lightweight and optimized to avoid impacting the user's browsing
performance. For ambiguous cases, the system relies on the Gemini API rather than local AI
models, which introduces a dependency on network availability but avoids the memory and
processing overhead of running language models in the browser.

3.1.2 Privacy-First Policy Compliance: The system is constrained by a strict privacy-first
requirement. No raw text or sensitive data can be transmitted to the Admin Dashboard; only
anonymized metadata and risk classifications may be sent, which limits the depth of centralized
analytics. In ambiguous detection cases where Regex alone cannot determine sensitivity, only
pre-masked text segments are sent to the Gemini API for classification. All structured sensitive
data identified by Regex such as API keys, passwords, and national IDs is replaced with
placeholder tags (e.g., [API_KEY], [PASSWORD]) before any external transmission.

3.1.3 Browser Security Sandboxing: Operating as a browser extension limits our access to the
system's underlying hardware. We are constrained by the Manifest V3 security standard, which
strictly controls how we can intercept user input across different AI platforms like ChatGPT,
Gemini and Claude.

3.1.4 Real-time Latency (Usability): To ensure high usability for diverse users, the local
Regex-based analysis must occur in near real-time. We have a hard constraint of a 200ms
processing window for local detection; exceeding this would degrade the user experience and
encourage users to disable the extension. For ambiguous cases that require secondary analysis
via the Gemini API, the total processing time including the API round-trip shall not exceed 1.3
seconds.

Hares AI. This is achieved by systematically managing inspections, reviews, and testing across
the entire Software Development Life Cycle (SDLC).

7.​ Problem Complexity

The development of Hares AI involves several dimensions of complexity that go beyond
standard software engineering challenges. The following points highlight the key areas of
complexity in this project.

7.1 Technical Complexity

The core challenge of Hares AI lies in accurately detecting sensitive data in real-time within a
browser extension environment. Unlike traditional applications, browser extensions operate
under strict security sandboxing rules defined by Manifest V3, which limits access to system
resources and restricts how scripts interact with web pages. Intercepting user input across
multiple AI platforms each with a different DOM structure requires platform-specific
implementations that must be maintained as these platforms evolve.

7.2 No Obvious Solution

There is no single established approach for real-time, privacy-preserving sensitive data detection
inside a browser extension. Existing solutions either rely on cloud-based processing which
compromises privacy or are limited to a single platform. Hares AI must balance detection
accuracy, processing speed, and privacy simultaneously, a combination that has no off-the-shelf
solution.

7.3 Multiple Disciplines Involved

The project spans multiple disciplines including cybersecurity, natural language processing, web
development, and software architecture. Each component, the extension, the backend, and the
admin dashboard requires different technical expertise and must be integrated seamlessly.

7.4 Significant Consequences

A false negative failing to detect sensitive data could result in a real data breach. A false positive
incorrectly blocking safe content could disrupt workflows and reduce user trust. Both failure
modes carry meaningful consequences, raising the stakes for detection accuracy.

7.5 Wide-Ranging Technical Issues

The system must handle diverse data types (structured and unstructured), multiple languages, and
constantly changing AI platform interfaces. Each of these variables introduces additional
complexity that must be addressed through robust design and testing.

12.​ System Architecture

Based on the functional and non-functional requirements of Hares AI, we selected the Layered
Architecture as the primary architectural style for the system. In this style, the system is divided
into distinct horizontal layers, each with a clearly defined responsibility. Each layer only
communicates with the layer immediately below it, which enforces strict separation of concerns
and prevents components from becoming tightly coupled.

                                           Figure 13. System Architecture.
The Hares AI system is organized into four layers:
Presentation Layer This layer contains all components that interact directly with the user.
It includes the Content Script UI (the alert overlays and masked-prompt views injected into AI
platforms such as ChatGPT, Gemini, and Claude), the Extension Popup (allowing the user to
view system status and configure personal settings), and the Admin Web Dashboard (used by

                                                                                                                             39
System Administrators and Department Administrators to view logs, statistics, and manage user
accounts).

This layer receives input from users and renders output, but contains no business logic.

Business Logic Layer This is the core of the system. It contains the Prompt Interceptor (which
captures the user's input before submission), the Regex Detection Engine (which locally scans
the text for sensitive data patterns across all risk categories), the Risk Classifier (which assigns a
risk level based on detection results and optionally invokes secondary AI classification), the
Policy Enforcer (which decides whether to block, warn, or allow the prompt based on
organisational policy), the Revision Generator (which produces a cleaned and structured
alternative for the user), and the Log Manager (which constructs and routes activity log entries).
None of the components in this layer depend on specific data storage technologies they operate
through abstractions provided by the layer below.

Data Access Layer This layer acts as the bridge between business logic and raw storage. It
contains the Chrome Storage API Client (for reading and writing configuration and cached data
within the browser), the Gemini API Client (for securely sending masked text to Google's
Gemini API when secondary classification is required), and the Firebase Client (for
authenticating users and synchronising logs and user configurations with Firestore).

Data Layer This layer holds the physical data stores. It contains Chrome Local Storage (for
extension settings, detection policies, and temporary prompt caches) and Firebase Firestore (for
persistent storage of user accounts, activity logs, and organisational configurations).

This architecture was chosen for Hares AI for the following reasons. First, the separation
between the Presentation Layer and the Business Logic Layer means that the extension's UI
components can be updated or restyled without any risk of breaking the detection pipeline.
Second, isolating the Regex Detection Engine and Risk Classifier in the Business Logic Layer
means that detection patterns and risk thresholds can be tuned without touching the storage or UI
code. Third, the Data Access Layer shields the business logic from knowing whether data is
stored in Chrome Storage or Firebase, a critical flexibility given that the extension operates both
locally and with optional cloud sync. Fourth, the Layered style naturally supports the system's
privacy-first requirement: raw sensitive text never leaves the Business Logic Layer; only masked
text is passed down to the Data Access Layer when an external API call is needed.

Supporting Pattern Event-Driven Architecture

The Layered Architecture is complemented by an Event-Driven pattern at the browser extension
level. Chrome's Manifest V3 extension model is inherently asynchronous: the Content Script
runs inside the AI platform's tab, the Background Service Worker runs in a separate isolated
context, and the Popup runs in its own window. These components cannot share memory

                                                                                                                             40
directly; they communicate exclusively through Chrome's message-passing API.

This event-driven communication is used as follows. When the Content Script detects that the
user has initiated a prompt submission, it fires a message carrying the prompt text to the
Background Service Worker. The Service Worker runs the full detection pipeline (Regex → Risk
Classification → Policy Decision) and fires a response message back to the Content Script
specifying the action to take (block, warn with masked version, or allow). This design keeps the
heavy processing off the UI thread and ensures that the extension remains responsive even
during complex regex evaluation or API calls.

Alternative Architectural Styles Considered

Model-View-Controller (MVC)

MVC is one of the most widely adopted architectural patterns for interactive applications. It
separates the system into a Model (data and business rules), a View (user interface), and a
Controller (intermediary that handles user input and updates both Model and View). We
considered MVC because it is familiar, well-documented, and maps cleanly onto many web
applications.

However, MVC was not appropriate for Hares AI. MVC assumes a single shared runtime where
the View, Controller, and Model can hold references to one another. A Chrome extension does
not have a single runtime: the Content Script, the Background Service Worker, and the Popup
each operate in isolated JavaScript environments with no shared memory. Attempting to apply
MVC would require forcing an artificial Controller onto one of these contexts, creating unnatural
coupling between components that cannot directly communicate. Furthermore, MVC does not
enforce the strict data-flow isolation that Hares AI requires, in particular, the guarantee that raw
sensitive text never reaches the storage or API layers. The Layered Architecture makes this
boundary explicit and structural, whereas MVC would require it to be enforced only by
developer convention.

Client-Server Architecture

The traditional Client-Server model treats the system as a thin client that sends requests to a
centralized server, where all business logic and data storage reside. We considered this approach
because Hares AI does have a server-side component (Firebase for user management and log
storage) and an external API dependency (Gemini for secondary classification).

Client-Server was rejected for two fundamental reasons. First, it directly contradicts the system's
most critical non-functional requirement: privacy. In a client-server model, the user's prompt text
would be transmitted to a server for processing. Even if that server were trusted, the mere
transmission of potentially sensitive data over the network introduces a point of exposure. Hares
AI's core value proposition is that sensitive data is detected and masked locally, on the user's
machine, before anything is sent anywhere. Second, the client-server introduces a single point of
failure. If the server is unavailable, the extension cannot function. Hares AI is designed to
continue operating offline using its local Regex Detection Engine, with the Gemini API call
being an optional enhancement rather than a hard dependency. The Layered Architecture
supports this graceful degradation naturally.

                                                                                                                             41
Microservices Architecture

Microservices decompose the system into a collection of small, independently deployable
services that communicate over a network (typically via REST or message queues). We
considered this approach because Hares AI has several logically distinct capabilities detection,
classification, logging, revision generation that could theoretically be separated into services.

Microservices were rejected because the operational overhead is disproportionate to the project's
scale and team size. Each microservice requires its own deployment pipeline, health monitoring,
API versioning, and inter-service security. More critically, all network-based inter-service
communication would reintroduce the same privacy exposure risk identified above: prompt text
(even masked) would transit a network boundary at every pipeline step. The Layered
Architecture achieves the same logical separation of concerns within a single process, without
the infrastructure complexity or the privacy risk.

Implementation Constraints Affecting Architecture

Several constraints shaped the architectural decisions described above:

Chrome Manifest V3 Restrictions Manifest V3 prohibits persistent background pages and
restricts the use of remote code execution. Background processing must be implemented as a
Service Worker, which can be terminated by the browser at any time and must re-initialise on
demand. This forces all states that must persist between events to be stored explicitly in Chrome
Storage, rather than in module-level variables.

No Raw Data Transmission The system's privacy requirements prohibit transmitting unmasked
prompt text to any external service. This constraint is enforced architecturally: the Gemini API
Client in the Data Access Layer only accepts pre-masked text from the Risk Classifier. The
masking step is structurally required before the data reaches the layer that has network access.

Cross-Browser Portability Limitation The current architecture relies on Chrome-specific
APIs. This limits deployment to Chromium-based browsers (Chrome, Edge, Brave). Extending
to Firefox would require replacing the Data Access Layer's Chrome Storage API Client with the
WebExtensions-compatible API equivalents.

Offline-First Detection The Regex Detection Engine must function without network access.
The architecture satisfies this by placing all local detection inside the Business Logic Layer,
which has no dependency on the Data Access Layer's network clients. The Gemini API Client is
invoked only when the Risk Classifier determines that the regex result is ambiguous, making the
external call an optional enhancement rather than a required path.

15.1 Local Regex-Based Sensitive Data Detection

FUNCTION LocalRegexDetection(rawPrompt : String) : List<Detection>

   // Step 1: Initialise empty results container
   detections ← []

   // Step 2: Load pattern dictionary from Chrome Storage
   // Patterns are stored externally to allow updates without redeployment
   patternDictionary ← GetRegexPatterns() // Map<Category, CompiledRegex>

   // Step 3: Apply every pattern to the raw prompt
   FOR EACH (category, pattern) IN patternDictionary DO

      matches ← pattern.FindAllMatches(rawPrompt) // non-overlapping

      FOR EACH match IN matches DO
         detection ← {
            category : category, // e.g. API_KEY, EMAIL, CREDIT_CARD
            value : match.Value,
            startIndex : match.StartIndex,
            endIndex : match.EndIndex
         }
         ADD detection TO detections

      END FOR
   END FOR

   // Step 4: Remove duplicate / fully-overlapping detections
   // If detection B is fully contained within detection A, keep A and discard B
   detections ← RemoveOverlaps(detections)

   // Step 5: Sort ascending by startIndex for downstream masking (Algorithm 15.2)
   SORT detections BY startIndex ASCENDING

   RETURN detections

END FUNCTION

// Helper
──────────────────────────────────────────────────────────────
FUNCTION RemoveOverlaps(detections : List<Detection>) : List<Detection>

   result ← []
   FOR EACH d IN detections DO

      dominated ← FALSE

                                                                                                                             63
      FOR EACH other IN detections DO
         IF other ≠ d AND other.startIndex ≤ d.startIndex
                  AND other.endIndex ≥ d.endIndex THEN
            dominated ← TRUE
            BREAK
         END IF

      END FOR
      IF NOT dominated THEN ADD d TO result END IF
   END FOR
   RETURN result
END FUNCTION

15.2 Sensitive Data Masking

FUNCTION MaskSensitiveData(rawPrompt : String,
                     detections : List<Detection>) : String

   // Step 1: Work on a mutable copy
   maskedPrompt ← rawPrompt

   // Step 2: Iterate in DESCENDING startIndex order
   // Replacing from the end backwards prevents index positions
   // of earlier detections from shifting after each replacement
   FOR EACH detection IN REVERSE(detections) DO

      placeholder ← '[' + detection.category + ']'
      maskedPrompt ← ReplaceSubstring(

         maskedPrompt,
         detection.startIndex,
         detection.endIndex,
         placeholder
      )
   END FOR

   // Step 3: Return the fully masked text
   // At this point NO raw sensitive value remains in the string
   RETURN maskedPrompt

END FUNCTION

15.3 Risk Classification and Policy Decision

FUNCTION ClassifyRiskAndDecide(detectedCategories : List<String>,
                        maskedPrompt : String,
                        activePolicy : PolicyConfig)
                        : ClassificationResult

// Step 1: Load the fixed category → risk level mapping

// HIGH : Authentication & Secrets, Financial & Banking,

//  Personal Identity, Cryptography & Certificates,

                                                                   64
//  Developer Secrets

// MEDIUM : Contact Info, Network & System Data, Location,

//  Legal & Government, Vehicle, Corporate & Document,

//  File & Path, Digital Fingerprints, Shipping & Logistics,

//  Dates & Time, Logs & Headers, Numeric Sensitive,

//  Education-Related

// LOW : Keyword-Based Sensitive Patterns only

riskMapping ← GetCategoryRiskMapping() // Map<Category, RiskLevel>

// Step 2: Find the highest risk level across all detected categories
highestRisk ← NONE
FOR EACH cat IN detectedCategories DO

   categoryRisk ← riskMapping.GetRiskLevel(cat)
   IF categoryRisk > highestRisk THEN

      highestRisk ← categoryRisk
   END IF
END FOR

// Step 3: Determine whether Gemini secondary classification is needed

// Trigger condition: NO categories were detected locally AND

//  the masked prompt exceeds 200 characters

requiresGemini ← (highestRisk = NONE) AND (LENGTH(maskedPrompt) > 200)

// Step 4: Apply the policy to translate risk level → preliminary action
// Default mapping : HIGH → BLOCK | MEDIUM → WARN | LOW → INFO | NONE → ALLOW
// Policy overrides : e.g. force WARN instead of BLOCK for a specific department
preliminaryAction ← activePolicy.GetActionForRiskLevel(highestRisk)

19.​ Conclusion

Hares AI addresses an important and growing security challenge caused by the rapid use of AI
tools in workplaces. As employees increasingly rely on platforms such as ChatGPT, Gemini, and
Claude, organizations face a higher risk of accidental exposure of sensitive information,
including passwords, API keys, personal data, financial records, and confidential business
content. This project proposes a practical solution that focuses on prevention at the point where
the risk begins: before the prompt is submitted to an AI platform.

The system was designed as a lightweight browser extension supported by an admin dashboard
and secure backend services. Its main strength is the privacy-first detection approach, where
prompt analysis is performed locally using Regex patterns whenever possible. Sensitive data is
masked before any further processing, and only anonymized metadata is stored for monitoring
and auditing purposes. For ambiguous cases, the system uses the Gemini API only after detected
sensitive content has been replaced with placeholder tags, which supports the project’s goal of
reducing exposure while maintaining useful detection capabilities.

Throughout the project, we defined the system requirements, use cases, analysis classes,
interaction diagrams, design classes, architecture, database schema, algorithms, expected
deployment, and test scenarios. The proposed architecture separates the presentation layer,
business logic layer, data access layer, and data layer, making the system easier to maintain,
extend, and test. The event-driven behavior of the browser extension also supports real-time
prompt interception while keeping the user experience responsive.

In conclusion, Hares AI provides a clear and feasible solution for protecting organizations from
unintentional AI-related data leakage. By combining local detection, risk classification, user
alerts, prompt blocking, compliant prompt revision, anonymized logging, and administrative

                                                                                                                             79
monitoring, the system balances security, privacy, and usability. Future work may include
improving detection accuracy through larger test datasets, expanding support to additional
browsers and AI platforms, enhancing policy customization for different departments, and
conducting real-world user testing to evaluate performance and usability in organizational
environments.
