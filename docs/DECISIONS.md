# Hares AI Web: Decisions (source of truth)

## Scope

Web only: React frontend (3 role dashboards + public pages) and NestJS backend API.
The browser extension is built separately. The API contract is the bridge.
Source requirements: Hares AI project report (Part-I). Any technology named there is NOT binding.

## Stack

TypeScript everywhere. React (Vite), NestJS, PostgreSQL.
Monorepo: web/, api/, contract/ (Zod schemas, generated OpenAPI). ORM: Prisma. UI: shadcn/ui with Radix and Tailwind (pending evaluation of the DGA Platform Code library).

## Decisions

1. Single organization per deployment. Keep a clean path to multi-tenant later.
2. The backend NEVER receives or stores prompt text: no original, no masked, no revised.
   It stores metadata only: event time, platform, data categories, risk level, action.
   The log endpoint uses a strict allowlist of fields and rejects unknown fields.
   The revised prompt is generated and shown inside the extension only.
3. Onboarding: user self-registers -> status PENDING (no department, no role, no access).
   System Admin approves and assigns department and role, or rejects.
   First System Admin comes from a seed script.
4. Roles: SYSTEM_ADMIN, DEPARTMENT_ADMIN, USER. Department Admin cannot approve new users.
5. Admin can define Custom Detection Rules:
   kind = PATTERN (regex) | KEYWORD (word list) | TOPIC (natural-language description).
   Each rule has: name, definition, risk level, action, scope (org-wide or departments), enabled.
   The backend stores and distributes them as a versioned policy bundle.
   The extension decides how to execute each kind and ignores unsupported kinds.
   Regex must be length-limited and validated (ReDoS). The UI warns admins not to put real secrets in TOPIC examples.
6. Policy: per department, category -> action (allow / warn / block) and enabled categories.
7. The extension pulls the policy bundle on startup and periodically using a version check, and keeps the last copy if the backend is down.
8. Log ingestion is idempotent: log_id (UUID) is generated by the extension.
9. UI and design compliance:
   - The web UI follows Saudi DGA design guidelines (design tokens, typography, components, patterns).
   - Arabic and English are both first-class, with full RTL support and content parity. Language switching is available on every page.
   - Target accessibility: WCAG 2.1 AA, mobile-first responsive layout.
   - Do not claim official DGA certification; compliance is checked by review and manual validation.
10. NONE-risk events are logged (needed for totals and allow-vs-block ratios).
11. Activity logs are retained 90 days, then deleted. The admin audit trail is append-only and never deleted.
12. The extension authenticates with an access token issued at login. Tokens are revoked immediately when a user is deactivated or rejected. Role or department changes take effect on the next policy bundle fetch.
13. Default risk for categories the report left unassigned: Health/Medical = HIGH, Account & Application = MEDIUM, Universal Identifiers = LOW, Region-Specific Banking & Identity = HIGH.
14. Only System Admin edits organization policy, department policy overrides, custom rules, and departments. Department Admin is read-only on these.
15. Password reset: emailed single-use link, 30-minute expiry, rate limited.
16. Users cannot export their own logs. CSV export is for administrators only.
17. Multiple System Admins are allowed. Only a System Admin can grant or revoke SYSTEM_ADMIN. Nobody can deactivate or demote their own account.
18. Departments are managed by System Admin only. Deactivating a department blocks log ingestion for its users.
19. Audit trail fields: acting admin, action, target, timestamp, non-sensitive details.
20. Deactivated users keep their historical logs. Reactivation is done by System Admin.
21. Log events carry a user_decision field (what the user did after the warning) and an optional rule_id (custom rule that matched). The ingestion contract is versioned with schema_version.
22. Password policy: minimum 8 characters with at least one uppercase letter, one lowercase letter, one digit, and one symbol. Login uses progressive throttling per account and per source address (increasing delay after repeated failures). There is no hard account lockout.
23. Logs of a deactivated department stay visible to administrators until the normal 90-day retention purge removes them.
24. A REJECTED account stays terminal. A System Admin may re-open it to PENDING. Rejected records are not deleted or purged.
25. Activity counters (aggregates) are retained indefinitely and carry no user identity. Only detail logs are purged at 90 days.
26. The per-user dashboard reads detail logs, so it shows at most the last 90 days.
27. Deployment assumption: web and API are served from one origin behind a reverse proxy, and the API runs as a single instance.
28. The extension-facing contract is defined as Zod schemas in contract/ and the OpenAPI document is generated from them.
29. Registration may reveal that an email is already registered (accepted). Login and password reset never reveal whether an account exists.
30. The extension session uses an access token of at most 1 hour plus a rotating refresh token that is revocable server-side. The extension never stores the user's password. This refines decision 12.
31. Policy, logs and dashboards work at the level of the 24 data categories. Organization-specific data types are handled by custom detection rules. The category codes are stable UPPER_SNAKE strings shared with the extension and are listed in docs/DATA-MODEL-BRIEF.md.
32. Password hashing uses bcrypt with cost 12 or higher. Passwords longer than 72 bytes are rejected.
33. Log ingestion validates event_time: events more than 5 minutes in the future or older than 90 days are rejected. Retention is based on event_time.
34. The extension has a logout endpoint that revokes the refresh token family. All JSON fields in the contract are snake_case. The policy bundle is one resolved list of 24 category entries plus the enabled custom rules and a version.
35. Web auth (B4a): access JWT is HS256 signed with JWT_ACCESS_SECRET, claims are only sub, tv (token_version), iss and aud. aud is the client kind (web or extension), so a web token never works on extension routes and the reverse. Role, status and department are always read from the User row by the guard.
36. Refresh tokens are 32 random bytes stored as SHA-256 hashes, bound to their client type (new column RefreshToken.client_type). Each rotation gives the successor a fresh 30-day expiry (sliding session). Reuse detection is strict: a replayed or concurrently reused token revokes the whole family, so every client must serialize its refresh calls: the web client across tabs (single-flight with the Web Locks API, B10), and the extension inside its service worker (one in-flight refresh promise shared by popup and content scripts).
37. The web refresh cookie is hares_rt: HttpOnly, SameSite=Strict, Path=/api/auth, Secure in production (COOKIE_SECURE overrides). All /auth routes reject a browser Origin that is not in CORS_ORIGIN (blocks login CSRF and cookie misuse); production CORS_ORIGIN must list the public web origin. Rotation and revocation of one refresh family are serialized with a PostgreSQL advisory lock, so a logout racing a refresh cannot leave a live token.
38. Login reveals the account status (PENDING / REJECTED / DEACTIVATED) only after the password is verified, and spends one bcrypt comparison even for unknown emails, so it never reveals whether an account exists (decision 29).
39. Every API route is authenticated by a global JwtAuthGuard unless marked @Public(). GET /auth/me returns the current account for the web shell.
40. Login throttle (B4c): per account and per source address, keys stored as SHA-256 hashes that include the client kind (web and extension are independent). Every attempt is reserved atomically in one SQL statement before the password is checked (a parallel burst cannot slip through); a correct password refunds it and clears the account counter. Account rule: 4 free attempts, then the next attempt waits 2, 4, 8 ... seconds, capped at 15 minutes; the counter resets only after 15 quiet minutes (window anchored to the last attempt), so waiting out delays never earns new free guesses. Source rule: same, with 20 free attempts (an organisation behind one NAT address must not be slowed by ordinary typos); a success does not clear it. Unknown emails are counted the same way. change-password uses the same rule keyed by the signed-in user. IPv6 sources are keyed by /64, IPv4-mapped addresses are unwrapped. On top, @nestjs/throttler windows per address: login 20/min, register 10/h, forgot-password 5/15 min, reset 10/15 min, change-password 10/15 min, default 300/min. TRUST_PROXY (hop count or proxy list; "true" refused) is required in production so req.ip is the real client. Follow-ups: the B8 purge job also deletes stale LoginAttempt rows; B7a gives ingestion a per-user limit instead of the per-address default window.
41. Password reset (B4c): forgot-password always answers 202 and does the lookup and email in the background (no timing leak). Only ACTIVE accounts get an email, at most 3 per account per 15 minutes; a new token invalidates older unused ones. The link is WEB_BASE_URL/reset-password#token=..., with the token in the URL fragment so it never reaches server logs or Referer; WEB_BASE_URL must be https in production. A password change also invalidates outstanding reset links. Reset and change-password bump token_version and revoke every refresh family (all web and extension sessions end); change-password then issues a new web session for the current device (WEB-FR-058).
42. Mail: nodemailer over SMTP; Mailpit in development and CI, a real SMTP provider in production (SMTP_HOST required there, STARTTLS required on a plain connection, timeouts set). Mail errors are logged by code only (SMTP messages can contain the recipient). In-flight reset emails finish on shutdown (enableShutdownHooks). The reset email is bilingual (Arabic first, RTL) and contains only the link and its expiry.
43. Audit writes (B4d): AuditService has only record / recordIn; admin services call recordIn with their own transaction client, so a change and its audit entry commit or roll back together. Detail is a flat record of short scalars (snake_case keys, at most 20 keys and 4 KB), with sensitive key names refused (password, token, secret, key, prompt, definition, ...). target_id may be null only for POLICY. The contract enums are checked at compile time against the Prisma enums.
44. Tests never touch the dev database: a vitest globalSetup creates hares_test_<random> for each run (migrate deploy, roles.sql grants, audit revoke, seed), points DATABASE_URL / APP_DATABASE_URL at it, and drops it at the end; stale test databases from killed runs are dropped at the next start. If the server is unreachable the URLs are blanked and the DB suites skip (fail closed); fixtures refuse to run on any database not named hares_test_*.
45. RBAC (B5a): the capability matrix lives in contract/src/capabilities.ts (ALLOW / SCOPED / DENY per role) and is the single source for the API guard, the web route guards and the tests. RolesGuard runs after JwtAuthGuard and fails closed: a non-public web route without @RequireCapability is refused, a Department Admin without a department is refused on department-scoped capabilities, and an extension token never passes a web capability. matrix.spec.ts reads the real route table and checks every DENY cell, so routes added later are covered automatically. Department scope always comes from the guard-loaded user row, never from a token claim.
46. Departments (B5a): never deleted, only deactivated (blocks ingestion via DepartmentsService.isActive). Names are unique case-insensitively. An inactive department can still be renamed. Every write audits in the same transaction.
47. roles.sql (B5a): the app role has no access to _prisma_migrations and only SELECT on DataCategory (reference data written by the seed). The REVOKEs sit after the broad GRANT in the same file; ops/revoke-audit-privileges.sql still runs last.
48. Users (B5b): every transition locks the target row (FOR UPDATE), checks the rules, changes status / role / department / approver in ONE UPDATE and audits in the same transaction. Deactivate and reject bump token_version and revoke refresh families; role and department changes take effect at once because the guard reads them from the database on every request. Grant SYSTEM_ADMIN clears the department (WEB-FR-064); revoke needs a new role and an ACTIVE department. A global advisory lock plus a re-read of the acting admin stops two System Admins from deactivating or demoting each other at the same moment. A Department Admin acts only on plain USERs of their own department (out of scope is 403, per WEB-FR-015).
49. Policy (B6): org values and department overrides live in PolicyCategoryAction (department_id NULL = organisation). The effective value per category is department override > organisation value > built-in default (HIGH -> BLOCK, MEDIUM -> WARN, LOW/NONE -> ALLOW, enabled). Every write bumps the single PolicyVersion in the SAME transaction as the change and its audit entry; a write that changes nothing bumps nothing. A CustomRule and its CustomRuleDepartment links are written in one transaction (the deferred scope trigger checks them at commit). The bundle is read in one RepeatableRead snapshot, ETag = "p<version>-<hash(version, department)>", 304 on If-None-Match (weak and * accepted), Cache-Control private, and carries no auth material. A Department Admin sees only their own department among a rule's departments.
50. Rule definitions (B6): KEYWORD is one word or phrase per line (max 200 words of 64 characters, de-duplicated); TOPIC is free text up to 4000 characters, never parsed by the backend; PATTERN is at most 512 characters, kept verbatim (not trimmed) and MUST be compiled by the extension with the flag i only. PATTERN safety: valid regex under flag i, no backreferences, static analysis with redos-detector (a pattern it cannot prove safe within its budget is rejected, which is deliberately conservative; unbounded patterns with overlapping character classes such as a naive e-mail regex are refused), and an execution test on worst-case inputs. Analysis and execution run in worker threads with hard timeouts and a memory cap, at most 3 at a time. The unicode flag is not supported because the analyser cannot model it together with case-insensitivity. Audit entries for rules never contain the definition.
51. Ingestion (B7a): strict allowlist with extension error codes (UNKNOWN_FIELD lists the accepted field names and never echoes the received ones; INVALID_ENUM lists accepted values; UNSUPPORTED_SCHEMA_VERSION wins over other errors; EVENT_TIME_OUT_OF_RANGE). Identity and the department snapshot come from the live user row. ON CONFLICT (log_id) DO NOTHING RETURNING decides idempotency; categories and both counters are written in the same transaction only when a row was inserted, with categories sorted so concurrent events lock counter rows in one order. The per-address request window is skipped on /logs; a per-user limit of 120 events per minute applies instead (in memory), and bodies over 8 KB are refused. A rule_id must exist but is not checked against the user's department.
52. Logs (B7b): lists use keyset pagination on (event_time DESC, log_id DESC) with the timestamp carried as TEXT with microseconds from the database (a JS Date would round it and skip rows). Scope is applied in SQL from the guard-loaded user: a User sees only their own events, a Department Admin their department, a System Admin everything; a log outside the scope is 404. CSV export is administrators only, streamed in chunks of 1000 by keyset (at most 100000 rows), UTF-8 with BOM, CRLF, cells starting with = + - @ tab or CR are prefixed with a quote. Headers go out with the first chunk, so a database error before that is a normal JSON error and one after it aborts the download instead of ending a truncated file cleanly.
53. Dashboards (B8): department and organisation dashboards read only the counters (EventCounter for totals, platforms and risk; CategoryCounter for categories) and never write; the personal dashboard reads the user's live ActivityLog rows and is clamped to the last 90 days. Days are UTC calendar days and must be real days from 1970; the span is checked after defaults (max 366 days). Intercepted = WARNED + BLOCKED; override rate = SUBMITTED_ANYWAY among those.
54. Retention (B8): the purge cuts at midnight UTC of the day 90 days back, so detail rows live 90 to 91 days and a counter day is never half backed by detail rows. Reconcile recomputes only days strictly after that boundary day, from a temporary table built once, under SHARE ROW EXCLUSIVE locks on both counter tables with lock_timeout 3 s and a few retries; ingestion transactions have a 20 s timeout so they ride out the short pause. Counters for older days and the audit trail are never touched. The jobs (reconcile every 6 h, purge every 24 h, first run a minute after boot, JOBS=on|off) run in-process because the API is a single instance (decision 27); replicate only with an advisory lock. The purge also clears stale LoginAttempt rows and long-expired reset and refresh tokens.
55. Audit read (B8): GET /api/admin/audit is System Admin only and read-only; the keyset cursor carries the database timestamp as text with microseconds.
56. End-to-end (B8): pnpm --filter api e2e starts the real server process (tsx src/main.ts) against the throwaway test database and walks the main story over HTTP; it already caught a boot failure (a subclassed guard without explicit @Inject) that the in-process tests could not see. CI runs it.
57. UI libraries (B9, docs/SPIKE.md): React + Vite + TypeScript; Radix UI primitives and our own components with Tailwind v4 (shadcn/ui pattern); tokens in one file (web/src/index.css) following the government design-system layers (primitive -> semantic), DGA-aligned but NOT official: the official Platforms Code values and package could not be verified and the third-party @dev-dga library is unaffiliated, closed-source and unproven, so neither is used. No DGA certification claim (decision 9). Font: IBM Plex Sans Arabic for Arabic and Latin. Western digits everywhere (data stays unambiguous in both languages).
58. Charts (B9): Apache ECharts, SVG renderer, tree-shaken. Every chart is mirrored by one function (applyDirection) for RTL, its container is always dir=ltr, it is created only after the web font is loaded, comparisons are horizontal bars, and every chart is followed by a "show data as a table" disclosure (the accessible fallback). Risk is never conveyed by colour alone.
59. Web client rules (B9/B10): the SPA proxies /api in development (one origin as in production); forms reuse the Zod schemas from @hares/contract; server state in TanStack Query; refresh calls are single-flight across tabs (Web Locks, decision 36).
60. UI mock (docs/design/prototype, made with Claude Design) is the visual reference for the web app: same tokens (index.css), fonts, component look and shell layout. Mapped to the real product: no prompt text anywhere (metadata and categories only, decision on privacy), no fake marketing numbers on the landing page, navigation built from the role matrix (NAV in auth/routes.ts). DGA alignment is by design principles only; no certification claim. Light and dark themes via data-theme; Arabic is the default language, Western digits.
61. Session safety (B10 review): only a 401 on refresh signs the user out (5xx/429/network keep the session); a generation counter stops a refresh that was already in flight from undoing a logout; the query cache is cleared whenever the session becomes anonymous; the reset token is read from the URL fragment and removed from the address bar.
62. Department Admin screens (B13): `/dashboard` is the department dashboard for a Department Admin (personal view for a User); new endpoint GET /dashboard/department/top-users lists the 5 users with the most HIGH events from live log rows (90 days at most, metadata only, department pinned from the token; a System Admin passes department_id). Department policy and rules are read-only; the API itself never sends the text of a TOPIC rule to a Department Admin (decision 30), the screen shows a hidden marker. A Department Admin can only deactivate plain users of their department, after a confirmation dialog; CSV export uses the same filters as the list and is saved from the page with the signed-in token.
63. System Admin screens (B14): every account action lives in one "Manage" dialog that offers only what the account's status allows (role, department, grant/revoke System Admin, deactivate, reactivate, reopen); the department select never preselects a hidden value (only ACTIVE departments are offered) and a signed-in admin has no deactivate or revoke for their own account. Policy edits save per category at once, one at a time; a department override can be removed. Rules are created and edited, never deleted (disable instead); a TOPIC form warns not to enter real secrets, and the server's verdict on an unsafe PATTERN is shown under the field and cleared when the field changes. After any admin change the users, pending, departments, audit, dashboard, policy and rules caches are reloaded (features/common/invalidate.ts), so no screen shows stale data.
64. Release packaging and checks (B15): the API ships as ONE esbuild bundle (the contract is compiled into it; Nest, Prisma, bcrypt and the regex analyser stay installed packages) run by plain Node; the web app is split per route so the chart library loads only on dashboards. Production is two images behind a TLS terminator: nginx (serves the app, proxies /api, writes the client address itself, so TRUST_PROXY=1) and the API; a one-shot `migrate` job (migrations, application role and audit lock in ONE transaction, seed) runs before the API, which receives only the settings it needs (never the owner database URL or the first-admin values) and refuses to start with the example placeholder secrets. PostgreSQL is a managed service; a role is cluster-wide, so environments on one cluster need different application role names. `pnpm e2e` runs a real browser against the real API on a throwaway database (sign-in, role matrix, ingestion, CSV, RTL, axe WCAG 2.2 AA on every screen); it does not test the production packaging, which CI only builds and the release checklist exercises by hand (docs/audit.md). The DGA review's design changes (type size, required marks, phone tables, dialog button order) are recorded there as follow-ups for the design refinement; no DGA certification is claimed anywhere.

## Schema (adapted from the old ER)

Keep: Department, User, ActivityLog.
Remove: Prompt, RevisedPrompt, DetectionResult.
User: status enum (PENDING/ACTIVE/REJECTED/DEACTIVATED), role and department_id nullable until approval, passwordHash, unique email.
ActivityLog: log_id UUID, user_id and department_id (both derived server-side from the access token; department is a snapshot), platform, risk_level, action, classification_source, user_decision, rule_id (nullable), schema_version, event_time, received_at.
LogCategory: log_id, category_code (many per log).
Add: DataCategory, PolicyCategoryAction, CustomRule, CustomRuleDepartment, PolicyVersion, AdminAuditLog, EventCounter, CategoryCounter, RefreshToken (hashed), PasswordResetToken (hashed).
Final schema is produced by the Systems Architect.
